# Phase 5B — Generated Page Integrity & URL Semantics Forensic Audit

**Mode: READ-ONLY.** No repository file was modified, no generator ran in write
mode, no HTML was regenerated on disk, no routes were corrected, no URLs were
renamed, no datasets changed. Verified at the end via filesystem hash diff
(§Repository Integrity) — zero drift.

---

## Executive Summary

**The Phase 5A anomaly was SYSTEMIC, not isolated.**

Phase 5A fixed one page (`womens-size-8-us-to-eu-dress.html`) whose route data
claimed a `from_region`/`size` combination the dataset didn't support. This
audit found **31 more pages with the exact same class of defect** — routes
that claim a source region/size the dataset contract rejects — plus **one
additional, independent, pre-existing instance** of the same class
(`eu-50-jacket-to-us-size.html`), for **32 total pages (25% of the clothing
generated-page ecosystem) sending users into a dead-end conversion state.**

**The evidence is precise about *why*:** 31 of the 32 share one root cause —
`expandClothingRoutes()` in `scripts/generate-phase10-pages.js` assigns
`size: row.us` to **every** direction-pair it generates, including the
reversed pairs (`EU→US`, `UK→US`), where that value should have come from the
row's `eu`/`uk` column instead. This silently produces routes like "EU pants
size 28" when the dataset has no such value (EU pants only go 42–56) — the
same shape of bug Phase 5A found by hand, just not yet found everywhere it
occurs. The 32nd case (the jacket page) is unrelated: a singleton hand-authored
route claiming a numeric EU jacket size, but "jackets" is a pure data alias to
"tops," which uses letter sizing in EU — there has never been a numeric EU
value to match against.

**The good news, equally evidence-based:** zero pages display a *wrong number
as if it were correct* (P0 count: **0**). The generator's own `toSize`/`null`
guard already prevents fabricated answers — the failure mode across all 32 is
"no answer shown, user sent to a dead end," not "wrong answer shown as fact."
Content generation is architecturally sound: every field on every page (title,
description, H1, preview, CTA) is provably derived from one single route
object in one function — confirmed by regenerating all 126 pages in memory
from current route data and diffing byte-for-byte against what's on disk.
Aside from the two known/newly-found route-validity bugs, the only other
finding is 89 pages with stale (but 100%-factually-correct) template wording
from an earlier version of the generator's description string — cosmetic, not
semantic.

## Methodology

**Baseline:** `git status --short` (1,031 modified files — unchanged carryover
from Phases 3/4/5A, all uncommitted) and `git rev-parse HEAD`
(`0dc41c5ad56cbdd1e34bc41d1f2b55d3e17b09b5`) recorded before any analysis. A
file-hash snapshot of `data/`, `clothing/`, `scripts/`, `programmatic/`,
`reports/` was taken before and compared after (§Repository Integrity).

**Route inventory:** reconstructed by reading `data/clothing_routes.json`
directly and re-running the exact `expandClothingRoutes()` logic from
`scripts/generate-phase10-pages.js` (read, not guessed) against
`data/clothing_sizes.json`. This is the same reconstruction Phase 5A used to
regenerate one page, extended here to reconstruct and audit all 126.

**Layer 1 — route↔page-content drift ("does the page on disk match what the
current route data says it should be?"):** intercepted `fs.writeFileSync` to
capture in-memory output instead of writing to disk (verified: **0 bytes
written to the real filesystem** — every one of the 126 "expected" renders
lives only in a JS `Map` in a throwaway Node process), then called the real,
unmodified `generateClothingProgrammaticPages()` (exported from
`scripts/generate-programmatic-pages.js` during Phase 5A) with the full
126-route array. Diffed the captured "expected" HTML against the actual
on-disk HTML for title, meta description, H1, CTA href, and lead-paragraph
conversion preview.

**Layer 2 — route↔dataset validity ("does the dataset actually support what
the route claims?"):** used the project's real, unmodified `app.js` contract
functions (`isValidClothingSize`, `getAvailableClothingSizes`,
`resolveClothingDataKey`) — required directly, not reimplemented, per the
audit's own instruction. This is the layer that actually caught both the
already-known and the newly-found defects; Layer 1 alone would have missed
all 32, because the pages faithfully and consistently reflect their (wrong)
route data — the drift is between the route and the dataset, not between the
route and the page.

**Filename semantics:** a token-based parser (not a single fixed regex) that
recognizes two conventions in use — the 120 machine-generated slugs
(`clothing-{gender}-{garment}-{size}-{FROM}-to-{TO}`) and the 6 irregular
hand-authored slugs — extracting whichever gender/garment/region/size tokens
are actually present and comparing only those against the route (fields not
encoded in a filename are not scored as mismatches).

**Conversion accuracy:** for every route with a dataset-valid source
combination, computed the actual target value via a direct, row-correct scan
of `clothing_sizes.json` (the same row-matching approach `app.js`'s
`getAllClothingConversions` uses) and checked whether the on-page preview text
mentions that exact value.

**Inbound references:** counted literal occurrences of each page's
`.html` filename across every other `.html`/`.xml` file in the repo (excluding
`reports/`) — an occurrence count, not a distinct-file count (one file can
reference a slug more than once, e.g. in both a cross-link block and a
sitemap).

## Architecture Findings

**SINGLE SOURCE**, confirmed two ways:

1. **By reading the code:** `generateClothingProgrammaticPages()` computes
   `title`, `description`, `body` (which contains the H1, the lead-paragraph
   preview, and the CTA href) all from the same local variables
   (`genderLabel`, `fromLabel`, `toLabel`, `categoryLabel`, `toSize`) derived
   once per iteration from the single `route` object. There is no second,
   independent code path that generates any of these fields.
2. **By the drift data itself:** across all 126 pages, **title, H1, and CTA
   query parameters matched the current route data with zero exceptions**
   (title_semantics: 126/126 PASS, h1_semantics: 126/126 PASS,
   cta_semantics: 126/126 PASS). The only drift found was in the
   description/preview *prose wording* — and even there, the underlying
   *facts* embedded in that prose (region codes, garment word, size token)
   matched the route in all 126 cases, with zero exceptions
   (`description_facts_match`: 126/126 true). A single-source architecture
   with a template that evolved over time produces exactly this signature:
   uniform, cosmetic-only drift in the fields that changed, perfect agreement
   everywhere else. A multi-source architecture would be expected to produce
   scattered, inconsistent drift — that is not what was found.

This matters directly for interpreting the rest of this report: **the Phase
5A bug and the 31 newly-found siblings were never a "page doesn't match its
own route" bug.** They are, without exception, "the route itself claims
something the dataset doesn't support, and the single content pipeline
faithfully — and only faithfully — rendered that wrong claim into a title,
description, H1, and CTA that all agree with each other and with the route,
and disagree with reality."

**All 32 invalid routes, with their exact root cause:**

| Cause | Pages | Detail |
|---|---|---|
| `expandClothingRoutes()` uses `row.us` as `size` for every direction pair, including reversed (`EU→US`, `UK→US`) pairs where it should use `row.eu`/`row.uk` | **31** | 24 women's tops/pants (US uses letters or a numeric scale in a different range than UK/EU for these garments — zero accidental overlap), 7 men's pants (US 28–40 numeric range doesn't overlap the EU 42–54 range used by those same rows) |

**Important sub-finding — a validity-check blind spot that does *not* produce
a defect here, but is worth recording.** `isValidClothingSize()` checks
whether a value exists *anywhere in a region's column* for that gender+garment,
not whether it exists *in the specific row* a route's number originally came
from. For men's pants, this coincidentally makes `clothing-men-pants-42-EU-to-US`
pass the validity gate (EU "42" is a real value — from a *different* row than
the one size "42" was generated from) — and it was checked end-to-end: the
generator's own row-correct lookup (`findClothingConversion`, used for the
on-page preview) independently finds the *correct* row and reports "EU 42
converts to approximately US 28," which is accurate. **This one case is not a
defect** — the page is functionally and factually correct — but it is a
coincidence of this dataset's specific numbers, not a guarantee. A future
change to the numeric ranges in `clothing_sizes.json` could make this gate
pass while producing a genuinely wrong-row answer, silently. Recorded as an
architecture note, not a page-level finding (see Recommended Remediation
Roadmap).

## Recommended Remediation Roadmap

**Per the audit's own rule: none of this was implemented. Recommendations
only, ordered by what they are, not by a claimed priority ranking beyond the
severity table above.**

1. **Immediate-fix candidate (well-scoped, mechanical, single root cause):**
   the `expandClothingRoutes()` bug in `scripts/generate-phase10-pages.js`
   (`size: row.us` used unconditionally for all 4 direction pairs) is the root
   cause of 31 of the 32 P1 pages. A fix would select the size value from the
   correct column (`row.eu`/`row.uk`/`row.us`) based on which region is
   actually `from_region` for that generated pair — analogous in shape to
   Phase 5A's `from_region` correction, but applied at the generator-logic
   level rather than to one hand-authored entry. Recommend a **dedicated
   remediation phase**, not a same-task fix, given the scope (31 pages, all
   requiring scoped regeneration and real-browser re-verification, mirroring
   Phase 5A's process).

2. **Dataset/content work (separate from #1):** `eu-50-jacket-to-us-size.html`
   is a standalone case — "jackets" has zero dedicated sizing data (it's a
   pure alias to letter-only "tops" data), so no numeric EU value will ever
   validate for it. Two paths, requiring a deliberate decision (not this
   audit's call): (a) correct the route to whatever the real, intended jacket
   conversion was meant to be if it's recoverable from context, or (b) accept
   that men's jackets cannot support numeric EU sizing under the current
   dataset and remove/redirect the page. Its 277 inbound occurrences make this
   non-trivial to resolve casually.

3. **Dedicated URL migration phase:** `womens-size-8-us-to-eu-dress.html`, as
   the user has already scoped. This audit adds no new candidates to that
   list (see §URL Migration Candidates) but confirms it remains the only one.

4. **UX/content polish (low priority, optional):** the 89 pages with stale
   template wording in their meta description and lead paragraph are
   factually correct today; refreshing their prose to match the current
   generator template is a cosmetic improvement, not a correctness fix. Could
   be folded into whatever full-site regeneration eventually happens for
   other reasons, rather than justifying one on its own.

5. **Intentional-acceptance candidates:** the 3 duplicate-semantic-intent URL
   pairs (§Route Integrity) are not broken — they're redundant. Whether to
   canonicalize one URL per pair (via `<link rel="canonical">` or a redirect)
   or simply accept the duplication is a policy call, not a defect fix.

6. **Architecture note, not a ticket:** the `isValidClothingSize`
   row-correspondence blind spot (§Dataset Integrity) currently produces no
   incorrect page, but is fragile — worth keeping in mind if
   `clothing_sizes.json`'s numeric ranges are ever edited, since a coincidence
   that currently saves one page (`clothing-men-pants-42-EU-to-US`) could just
   as easily start silently producing a wrong-row "valid" result elsewhere.
